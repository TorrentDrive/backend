# Continuous SemVer Release Pipeline & Unified All-in-One Packaging in Backend

`backend`, `frontend`, and `website` compute Semantic Versions from Conventional Commits, tag multi-architecture container images, update version and changelog manifests (`Directory.Build.props`, `package.json`, `CHANGELOG.md`), and publish GitHub Releases directly within the primary `main` workflow run (`[skip ci]`), rather than delegating release creation to `release-please` pull requests or maintaining a separate `deploy` repository. The unified all-in-one container (`Dockerfile`, `entrypoint.sh`, `config/`), Docker Compose topologies (`docker-compose.yml`, `compose/`), one-command installers (`install.sh`, `install.ps1`), and PaaS blueprints (`paas/`) live directly in `backend` and are smoke-tested (`smoke-test.sh`) and published (`ghcr.io/torrentdrive/torrentdrive`) in the same workflow (`docker-build.yml`) as the split service images. Documentation-only commits (`docs:` or `*.md`-only diffs) in `backend` and `frontend` run fast validation only and skip container image builds and SemVer releases, while `frontend` releases forward their SemVer `bump` level (`major`, `minor`, `patch`) via `repository_dispatch` (`build-combined`) to `backend` so the all-in-one image always ships the latest UI and backend in lockstep.
